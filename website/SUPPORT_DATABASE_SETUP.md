# 支持开发者数据库与支付接入

## 当前落地范围

生产环境使用独立的 Supabase 项目保存支持者账号、邮箱验证挑战、支付订单、权益和审计记录。它不与公开网站反馈共用数据库项目或 `service role`，以缩小密钥泄露时的影响范围。

执行顺序：

1. 新建专门用于支持者数据的 Supabase 项目。
2. 在这个项目的 SQL Editor 执行 `supabase/support-schema.sql`。
3. 服务端配置 `SUPPORT_SUPABASE_URL` 与 `SUPPORT_SUPABASE_SERVICE_ROLE_KEY`。
4. 分别生成数据加密密钥与查询 HMAC 密钥，配置 `SUPPORT_DATA_ENCRYPTION_KEY_BASE64` 和 `SUPPORT_LOOKUP_HMAC_KEY_BASE64`。

专用 `service role` 和两把数据密钥只能保存在网站服务端的密钥管理环境中，绝不能放入桌面 EXE、网页 JavaScript、安装包、日志或公开仓库。数据库没有为 `anon` 或 `authenticated` 创建访问策略，并对敏感表启用了强制 RLS。

## 数据与权益规则

- `support_accounts`：邮箱只保存带密钥 HMAC 查询值与 AES-256-GCM 密文，同时保存昵称和是否公开致谢。
- `support_email_challenges`：只保存带密钥验证码 HMAC，不保存明文验证码，并限制失败次数与有效期。
- `support_payments`：支付平台交易号只保存带密钥 HMAC，并保存商户订单号、金额、状态与验证来源；订单身份字段创建后不可修改。
- `support_entitlements`：保存支持者徽章、未来永久免广告与未来 Pro。
- `support_audit_log`：保存不含支付密钥和原始回调内容的审计事件。

数据库按“单笔已验证支付的最高金额”计算权益，不累计不同订单：

- 满 1 元：支持者徽章；
- 满 3 元：未来永久免广告；
- 满 5 元：未来 Pro。

重复支付回调不会重复生成权益。订单退款后，数据库会重新查看该账号是否仍有其他满足门槛的已支付订单，再决定是否撤销对应权益。

## 安全开关与商店政策

`payment_rewards_enabled` 默认是 `false`。这意味着数据库结构已准备好，但不会因第三方支付自动发放数字权益。

## 上线前安全清单

- Supabase 管理员账号启用 MFA，只给确有需要的人员访问权限。
- 网站托管平台使用加密的环境变量/Secret，不把密钥写入构建产物或客户端错误信息。
- 支付回调只接受 HTTPS；逐项验证平台签名、时间戳/随机数、商户号、应用 ID、订单号、金额和币种，并做重放保护。
- 验证码使用密码学安全随机数，服务端用带密钥 HMAC 保存；按邮箱 HMAC、IP HMAC 和时间窗口限流，连续失败 10 次立即失效。
- 公开致谢接口只能返回昵称，不返回账号 ID、邮箱密文、订单金额或支付流水信息。
- 日志禁止记录邮箱、验证码、支付回调原文、Authorization 请求头和私钥；只记录内部订单号与结果码。
- 配置数据库备份与恢复演练、异常登录和密钥使用告警；定期轮换 `service role`、支付密钥与应用密钥。
- 加密密钥轮换应采用版本化密文和后台重加密流程；轮换前保留受控旧密钥，否则历史邮箱无法解密。
- 明确定义数据保留期限。用户注销时删除验证码和非财务资料；依法必须保留的支付账目应去标识化并限制访问。

原因是 Microsoft Store 政策对“自愿捐赠后获得数字商品、附加功能或移除广告”有专门限制。数据库和微信/支付宝支付可以在技术上不依赖微软，但不能让 Store 版自动绕过审核规则。发布前应以当时最新政策和 Partner Center 的书面答复为准。

只有在非 Store 分发版本，或确认 Store 版允许该方案以后，才在服务端执行：

```sql
update public.support_program_config
set payment_rewards_enabled = true
where singleton = true;

select public.reconcile_all_support_entitlements();
```

## 微信支付与支付宝的正确链路

```text
桌面应用 -> 你的服务端创建 pending 订单
         -> 服务端调用微信支付/支付宝商户接口取得二维码或支付参数
用户付款 -> 支付平台异步通知你的服务端
         -> 服务端验证签名、商户号、订单金额和订单状态
         -> 标记 support_payments 为 paid
         -> 数据库触发器重新计算权益
应用登录 -> 邮箱验证码或以后接入的账号系统
         -> 服务端返回当前有效权益
```

不要根据客户端的“我已付款”按钮、支付截图或订单号直接自动发权益。个人收款码没有可靠的商户异步通知和签名验证，只适合人工核对，无法安全地批量自动赠送 Pro。

正式接入仍需要申请微信支付商户号、支付宝开放平台应用及对应支付产品。密钥只放服务端环境变量；项目目前只完成数据库与安全的数据访问层，未在缺少商户资料的情况下伪造支付回调。

## 支付平台是否收费

- 微信支付官方接入指引写明申请接入本身不收费；正式交易通常按类目收取交易服务费，官方给出的常见区间是交易额的 0.6%–1%，最终以商户签约页面为准：[微信支付接入指引](https://pay.wechatpay.cn/static/applyment_guide/applyment_detail_public.shtml)。
- 支付宝开放能力/API 本身不等于免交易费。实际费率取决于申请的支付产品、行业类目和签约页面；部分官方场景展示的标准费率为 0.6%，但不能把它当作所有软件商户的统一费率：[支付宝开放平台支付服务](https://open.alipay.com/paymentServicer/paymentServicer.htm)。

例如 5 元订单按 0.6% 粗算是 0.03 元，按 1% 粗算是 0.05 元；实际还要以平台的计费精度、优惠活动、退款规则和最终合同为准。除此之外，还可能有服务器、域名、邮件验证码和数据库超出免费额度后的成本。

## 邮箱与 Microsoft 账号

邮箱验证码只能证明用户控制该邮箱，不能证明这是 Microsoft Store 实际下载应用的账号。若以后必须确认 Microsoft 账号身份，应增加 Microsoft OAuth 登录并把稳定账号标识绑定到 `support_accounts`，不要只依赖用户手填邮箱。

对于自建 Pro，批量赠送不需要逐个修改 EXE：后台导入或确认订单后写入 `support_entitlements`，客户端登录同一支持者账号并从服务端查询权益即可。离线使用时可由服务端签发短期、可验证的权益凭据，客户端只做缓存，不把本地配置当作最终凭证。
